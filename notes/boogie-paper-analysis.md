# Boogie 2 Paper — Deep Analysis for CppVerify

Source: K. Rustan M. Leino, "This is Boogie 2" (Microsoft Research, KRML 178, working draft 24 June 2008). 52 pages.
Read fully on 2026-05-13. This document is the persistent reference for the IVL design patterns CppVerify's VCR IR is modeled after.

---

## 1. What Boogie is, in one paragraph

Boogie is an Intermediate Verification Language (IVL) — a formal-methods analogue of LLVM IR. Source-language verifiers (Spec#, Dafny, VCC, BML, Eiffel) translate their programs into Boogie, and Boogie then translates Boogie programs into SMT-LIB queries for Z3 (or other provers). Boogie itself does not verify; it generates verification conditions. As a language, Boogie has BOTH mathematical components (types, constants, functions, axioms — like a logic) AND imperative components (variables, procedures, implementations — like a program). The imperative part has `assert`, `assume`, `havoc`, assignment, `call`, `if`, `while`, `goto`, `break`, `return` — and that's it. This minimal set is sufficient to encode the semantics of virtually any imperative language.

**Why this matters for CppVerify:** our Layer 1 VCR IR IS a Boogie-like IVL, custom-built for C++. Our Layer 2 IR mirrors Boogie's basic-block translation. Our WP+Z3 path is the same as Boogie's. **Boogie is the architecture document for the system we are building.**

## 2. The seven Boogie declarations and their CppVerify analogs

| Boogie | What it is | CppVerify analog |
|---|---|---|
| `type` | Type constructors / synonyms | `VType` enum; we don't expose user-defined types in MVP |
| `const` | Symbolic constants | Implicit — we use SSA constants generated by Passivize |
| `function` | Mathematical functions (with optional body-as-axiom) | `spec` functions in CppVerify — encoded as Z3 `declare-fun` + axiom |
| `axiom` | Logical assertions about constants/functions | Generated automatically from `spec` function bodies |
| `var` | Mutable variables (the state) | Local variables + the heap |
| `procedure` | Specification (signature + pre/modifies/post) | `VFunction` with preconditions, postconditions, modifies |
| `implementation` | Procedure body | Function body in Layer 1 IR |

The 1-to-1 mapping is striking. CppVerify's IR is a domain-specific Boogie.

## 3. Memory modeling — §5.0 (the most important section for us)

Boogie shows three patterns for modeling heap memory. This is where the "Z3 array theory" approach we picked gets its theoretical grounding.

### Pattern 1: One Boogie variable per source-field (Spec#/Dafny early style)
```boogie
type Ref;
var C.data: [Ref]int;
var C.next: [Ref]Ref;
```
A source-level `o.data` becomes the Boogie expression `C.data[o]`.

### Pattern 2: Single polymorphic heap (our choice, simplified)
```boogie
type Field a;
type HeapType = <a>[Ref, Field a]a;
var Heap: HeapType;
const unique C.data: Field int;
const unique C.next: Field Ref;
```
A source-level `o.data` becomes `Heap[o, C.data]`.

**Advantages of Pattern 2 (per Boogie paper):**
- Conciseness: one variable, not one per field.
- Quantification over fields: `(∀ f:Field α • ...)` lets you write properties over fields not in scope at translation time. Crucial for modular verification.

### Pattern 3: Curried heap (ObjStore)
```boogie
var ObjStore: [Ref]<a>[Field a]a;
```
Useful when whole-object updates are frequent (e.g., copy constructors).

**CppVerify's choice:** we adopted Pattern 2 in spirit — a single Z3 array indexed by pointer addresses, with the element type derived from the pointee. For MVP we don't need polymorphism over field names; struct fields are encoded by flattening.

## 4. Frame conditions — §5.1 (THE pattern for `modifies`)

Boogie's `modifies` clause is **coarse-grained** — it lists which global *variables* can change, not which *locations*. For finer-grained framing (which is what CppVerify's `modifies(*p, x->field)` provides), Boogie uses a **postcondition** that quantifies over locations:

```boogie
procedure M(p: Ref);
  modifies Heap;
  ensures (∀ o: Ref, f: Field α •
            Heap[o, f] == old(Heap)[o, f] ∨
            (o == p ∧ f == C.data) ∨
            ¬old(Heap)[o, alloc]);
```

The postcondition reads: "for every location (o, f) in the heap, either it's unchanged, OR (o is the parameter AND f is the .data field), OR it's newly allocated."

**This is exactly what CppVerify's `modifies(...)` clause compiles to.** In Layer 1 IR we record `modifies: [VLvalue]`; in Z3 encoding we generate the equivalent quantified postcondition implicitly. The user writes the surface syntax; the verifier writes the Boogie-style frame postcondition.

## 5. States and execution traces — §7

Boogie's semantic model:
- A **state** maps variables to values.
- An **execution trace** is a (finite or infinite) sequence of states, optionally ending in `↯` (going wrong = a failed assertion).
- A trace can be: **terminating** (finite without ↯), **going wrong** (finite ending in ↯), or **diverging** (infinite).

This is the operational semantics framework our wp calculus implicitly uses. We don't need to expose traces — but we should think in these terms when reasoning about correctness of the encoding.

---

## 6. Procedures vs Implementations, and `free` clauses — §8

Boogie distinguishes:
- **Procedure**: specification only. Caller's perspective.
- **Implementation**: body. Callee's perspective.
- A procedure can have multiple implementations; each is verified independently.

**The `free` keyword is a MAJOR design feature** (§8.1):
- `free requires P;` — implementation assumes P, but callers don't have to prove it.
- `free ensures P;` — callers assume P after the call, but implementation doesn't have to establish it.
- `free invariant I;` — both parties assume I.

**Why this matters for CppVerify:**
- This is the mechanism for **trusted axioms** — properties the verifier accepts without proof (e.g., "Clang's typedefs are sound," "two unique_ptrs to different objects don't alias").
- It's also how we encode `recommends`: a `recommends(E)` clause is essentially a `free requires E;` from the caller's perspective (caller doesn't check it), but the verifier emits a separate diagnostic pass that DOES check it on failure.
- The asymmetry between caller traces and callee traces (§8.2) is what makes performance modular: free clauses let us skip rechecking facts we've already established.

**Caller traces vs callee traces are NOT the same** (§8.1). Free clauses create the divergence. CppVerify's implementation of `recommends` should encode this asymmetry explicitly.

## 7. Statements — §9 (the core of Layer 1 IR)

Boogie's complete statement vocabulary:
- `assert E` — VC obligation; must hold in every correct trace.
- `assume E` — hypothesis; renders traces where E is false infeasible.
- `havoc x` — assign x an arbitrary value (subject to `where` clauses).
- `Lhs := Expr` — assignment (including parallel: `x, y := y, x`).
- `call P(args)` and `call forall P(*, *)` — procedure invocation.
- `if`, `while`, `break`, `return`, `goto`, label statements.

**Every CppVerify VStmt has a direct Boogie analog.** Our IR is a restriction of Boogie's surface syntax (we don't have `goto`, since C++ ASTs are structured).

### The assert/assume duality (§9.2)

The semantic distinction is:
- `assert E`: traces where `E(σ)` is true continue; traces where it's false become `σ↯` (going wrong).
- `assume E`: traces where `E(σ)` is true continue; traces where it's false are removed entirely.

**The interplay:** `assert P; assume P;` is the canonical pattern for "we just proved P; from now on, we can use it." This is how loop invariants are encoded.

### The havoc + assume idiom (§9.4)

`havoc x; assume P(x);` produces "an arbitrary x satisfying P." This is the mechanism for:
- Modeling nondeterminism.
- Loop invariants: `havoc loop_vars; assume invariant;` represents an arbitrary post-iteration state.
- Function calls: `havoc modifies; assume postcondition;` represents "the callee did whatever it does, satisfying its post."

This idiom is the LOAD-BEARING construct of imperative verification. Our Passivize pass MUST implement it correctly.

## 8. Translation to basic blocks — §9.0–9.1

Boogie compiles structured code (if/while/break/etc.) into **basic blocks** of the form:
```
label: SimpleStmt* Goto;
```
where SimpleStmt is assert/assume/havoc/assignment/call and Goto is `goto labels;` or `return;`.

**This is what our Passivize pass produces.** Our Layer 2 IR is essentially a labeled CFG.

### Key transformations

**If with condition E** (§9.7):
```
if (E) Thn else Els
→
goto L0, L1;
L0: assume E;    Thn; goto Done;
L1: assume ¬E;   Els; goto Done;
Done:
```

This is **nondeterministic goto + assume** — Boogie's signature pattern. We pick one branch, the assume narrows it.

**While with invariant I** (§9.8):
```
while (E) invariant I; { body }
→
goto Head;
Head:
  assert I;                  // invariant holds on entry / preserved
  havoc loop_modified_vars;  // forget everything the loop touches
  assume I;                  // re-establish: we know I (free hypothesis)
  goto Body, Done;
Body: assume E; body; goto Head;
Done: assume ¬E;
```

**This is the textbook loop encoding.** It implements the wp rule for loops: prove invariant on entry, assume invariant for an arbitrary mid-loop state, prove invariant preserved after one iteration, exit with invariant + negated condition.

**Procedure call** `call x := P(E);` (§9.9):
- Equivalent to: assert P's pre with substitution, havoc modifies + x, assume P's post.
- This is the modular verification pattern we adopted.

**Call-forall** `call forall Lemma(*, *)` (§9.10):
- Equivalent to: `assume (∀x, y • Pre(x,y) ⇒ Post(x,y));`
- Useful for invoking a lemma universally without binding parameters.
- We don't need this in MVP, but it's a future-feature for proof functions.

## 9. Quantifiers and triggers — §4.4, §11.2

Boogie supports:
```boogie
(∀ x: T • {f(x)} body(x))
```
The `{f(x)}` is a **trigger** — a term-pattern that tells Z3 "when you see `f(x)` in the proof context, consider instantiating this quantifier with that x."

**Why triggers matter:** without good triggers, Z3 either:
- Over-instantiates (tries every possible value) → slow / runs out of memory.
- Under-instantiates (gives up) → incomplete (reports false unknown).

Default triggers are inferred from the quantifier body. User-supplied triggers override defaults. Restrictions on triggers:
- Must mention all bound variables.
- Cannot be a bare bound variable.
- Cannot contain logical operators or quantifiers (only function applications and arithmetic).

**For CppVerify:**
- Bounded `forall(i, lo, hi, body)` doesn't need a trigger — the bound IS the trigger when encoded as `(∀i • lo ≤ i ∧ i < hi ⇒ body)` since Z3 instantiates on the bound check.
- When we add unbounded quantifiers post-MVP, we MUST expose trigger syntax.

## 10. Attributes — §11

Boogie's attribute system `{ :attrName arg1 arg2 ... }` attaches metadata to almost anything:
- `{ :errorMessage "possible null deref on line 218" }` on an assert — used for diagnostics.
- `{ :bvbuiltin "bvadd8" }` on a function — directs Z3 to use its native bitvector adder.
- `{ :noInference }` on a variable — directs an inference tool to ignore it.

**For CppVerify:**
- We need attribute-style annotations on Layer 1 IR nodes to carry SourceLocation + error messages for diagnostics.
- Z3 native operations (bitvector ops, array ops) are exposed similarly via SMT-LIB attribute hints.

---

## 11. Polymorphic maps — §2.1

Boogie's most distinctive feature: maps can be polymorphic over their value types.
```boogie
type HeapType = <α>[Ref, Field α] α;
```
The `<α>` quantifies the map over a type variable. This single declaration handles ALL fields of ALL types in a single Heap.

**CppVerify doesn't need this in MVP** — we encode struct fields by flattening (separate Z3 constants per field), and we have only one heap (pointers to scalars). But if we ever want to handle arbitrary structs with pointer fields uniformly, Boogie's polymorphic map is the model.

---

## 12. Orders — §10

`<:` is a built-in partial order in Boogie. Used heavily for modeling class/interface hierarchies in OOP languages. `unique` constants are guaranteed distinct; `complete` declares a closed set of immediate children.

**For CppVerify:** not relevant in MVP (we don't model class hierarchies / virtual dispatch). When we add inheritance support post-MVP, this is the technique.

## 13. What Boogie validates about CppVerify's plan

Reading the paper end-to-end confirms multiple architectural decisions we made:

1. ✅ **Layered IR (structured Layer 1 → basic-block Layer 2)** — Boogie's §9.0–9.1 is exactly this.
2. ✅ **havoc + assume idiom for loops** — §9.8 is the textbook source.
3. ✅ **`modifies` + frame postcondition** — §5.1 is the canonical pattern.
4. ✅ **Procedure call as assert/havoc/assume** — §9.9.
5. ✅ **Z3 array theory for the heap** — §5.0 Pattern 2, simplified.
6. ✅ **Spec functions encoded as `function` + axiom** — §3 (function declarations with bodies = axioms).
7. ✅ **Bounded quantifiers don't need explicit triggers** — §11.2 confirms the bound's range check acts as a trigger.

## 14. What Boogie suggests we should ADD or refine

1. **`free` clauses** — we should add `free pre(...)`, `free post(...)`, `free invariant(...)` to our contract vocabulary. These are how trusted axioms are encoded. They're also the right semantic foundation for `recommends`.
2. **Attribute system on IR nodes** — `{ :errorMessage "..." }` is the right pattern for carrying diagnostic context through to Z3 output. We should put SourceLocation + a human message on every assert in Layer 2.
3. **Call-forall semantics for proof functions** — a `proof` lemma in CppVerify should support being invoked "for all" via `call forall Lemma(*, *)`. Post-MVP refinement.
4. **`unique` constants for type discriminators** — when we add structs with constructors or enums, this is the technique.
5. **Polymorphic maps in the encoder** — not for MVP, but the right answer for handling generic containers (e.g., `std::vector<T>`) without instantiating one heap per T.

## 16. The slogan

**The Verus paper showed us WHAT to build. The Boogie 2 paper shows us HOW to build it.**

Verus is the design target. Boogie is the construction manual. Together they cover the territory we're navigating. The remaining gaps — pointer reasoning without a borrow checker, integer-mode trade-offs, C++-specific semantics — are CppVerify's own engineering territory and not covered by either paper.
